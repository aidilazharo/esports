# Runtime folders and server deployment policy

The repository ignores these root directories via `.gitignore`:

| Directory | Deployment behavior | Purpose |
| --- | --- | --- |
| `html/` | **Clear all contents after a successful new-code server pull; leave empty directory** | Generated static pages regenerated by PHP |
| `uploads/` | Preserve local contents across deployments | School logos, images, certificates and user uploads |
| `download/` | Preserve local contents across deployments | Server-provisioned PDF downloads |

`git fetch` only downloads Git objects and does **not** change any working files, so the cleanup occurs when new code is actually checked out/merged or deployed, not on fetch alone.

## Option A: SSH-based safe pull (recommended for manually managed Git checkouts)

From the application's Git checkout on its `main` branch, use:

```bash
bash scripts/safe-pull.sh
```

The script backs up/restores `uploads/` and `download/` and runs `scripts/reset-html-cache.sh` when the revision advances. It never restores old generated HTML; `html/` is left empty after a successful new-code pull. A failed pull preserves existing files.

If your installation predates this repository cleanup, download the current script **before** the first pull, so previously tracked runtime files can be backed up:

```bash
curl -fsSL https://raw.githubusercontent.com/aidilazharo/esports/main/scripts/safe-pull.sh -o esports-safe-pull.sh
bash esports-safe-pull.sh
rm esports-safe-pull.sh
```

Keep a separate verified backup of the live database and uploads before deploying.

## Option B: Ordinary `git pull` with a server-local Git hook

Install once on the **server checkout** only:

```bash
bash scripts/install-server-html-hook.sh
```

This installs a Git `post-merge` hook that invokes `scripts/reset-html-cache.sh` whenever a merge/pull succeeds on `main`. Installation refuses to overwrite an existing `post-merge` hook or an existing custom hooks directory. After installation, normal successful `git pull` executions clear generated HTML.

## Option C: Hostinger hPanel Git auto-deployment

Hostinger may publish/replace files without executing the checkout's Git hooks. For deployments that bypass Git hooks, the application includes a **first-request PHP fallback**:

- `config.php` loads `includes/html_cache_deploy.php`.
- The fallback reads the root `VERSION`; if it differs from the observed deployed version, it empties `html/` once, then records the version in a file-lock-protected marker in the server's temporary directory.
- It refuses to clear an `html/` symlink, does not follow symlinks inside the cache, and leaves `uploads/` and `download/` untouched.
- As this runs on the first PHP request after the new version appears, the directory may not be cleared at the exact moment hPanel completes deployment. A failed or disabled version bump means the fallback cannot identify that revision; the server Git hook or safe pull remains the immediate alternative.

The public PHP header regenerates static pages as they are requested. `html/` therefore will not remain empty after visitors trigger new page generation.

**Important:** Git ignore rules do not control Hostinger's file-replacement behavior. If hPanel overwrites the entire deployment directory, ignored runtime files can still be lost. Store `uploads/` and `download/` in external persistent storage or use an exclusion-aware deployment setup and symlinks. Do not run `git clean -fdx` on production; it can remove ignored files.

`download.php` expects `download/metadata_jpn_esports.pdf` to exist on the server. New Git clones do not contain the PDF, upload folders or generated HTML.

## Security

The tracked root `.htaccess` prevents executable upload extensions from being served by Apache rewrite rules and denies HTTP access to `scripts/` and `database/`. Configure equivalent web-server rules when Apache `.htaccess` is not active. Keep upload permissions as restrictive as practical, and back up runtime directories independently of Git.
